# Deploying behind Apache + mod_jk (ColdFusion)

CommandBox rewrites URLs for you locally (`web.rewrites.enable` in `server.json`).
Apache does not. Without rewriting only `/` works and every other page 404s,
because no public URL in this CMS is a file on disk:

    /about-us
    /legal-services/wills/wills-blue-mountains/wills-katoomba
    /media/2026/08/photo.png      <- served by a handler, from outside the webroot
    /sitemap.xml                  <- generated per tenant

## The rules must live in the vhost, not in .htaccess

This is the part that costs an evening if you get it wrong, and the symptom does
not point at the cause.

**mod_jk ignores internal redirects.** It hooks Apache's `translate_name` phase
and skips any request where `r->prev` is set.

**Per-directory rewrites always produce an internal redirect** when they change
the URI — `.htaccess` and `<Directory>` blocks alike. They run in the `fixups`
phase, after the URI has already been mapped to a filesystem path, so
mod_rewrite cannot edit the URI in place and has to resubmit the request.

Put those together:

    1. /about-us arrives
    2. mod_jk translate_name: matches no .cfm pattern, declines   (correct)
    3. fixups: rewrite produces /index.cfm/about-us               (correct)
    4. internal redirect
    5. mod_jk translate_name again: r->prev is set, so it SKIPS   <-- the bug
    6. nothing claims the request; Tomcat answers 403

At **vhost level** mod_rewrite runs during `translate_name` itself and edits the
URI in place. No internal redirect, so mod_jk sees `/index.cfm/about-us` on its
normal pass, matches `/*.cfm/*`, and forwards it.

Same rules, same flags. Only the phase changes.

## Working vhost

```apache
<VirtualHost *:80>
    ServerName example.com
    DocumentRoot /var/www/sites/example.com/public

    JkMountCopy On
    JkMount /*.cfm cfusion
    JkMount /*.cfm/* cfusion

    RewriteEngine On

    # Already at the front controller.
    RewriteRule ^/index\.cfm(?:/|$) - [L]

    # Real files and directories served directly.
    RewriteCond %{DOCUMENT_ROOT}%{REQUEST_URI} -f [OR]
    RewriteCond %{DOCUMENT_ROOT}%{REQUEST_URI} -d
    RewriteRule ^ - [L]

    # Everything else to the front controller.
    RewriteRule ^/(.+)$ /index.cfm/$1 [PT,QSA,L]

    <Directory /var/www/sites/example.com/public>
        Options FollowSymLinks
        AllowOverride All
        Require all granted
    </Directory>

    DirectoryIndex index.cfm index.html
</VirtualHost>
```

Two differences from the `.htaccess` form, both easy to trip on:

| | Per-directory | Vhost |
| --- | --- | --- |
| Pattern | `^(.+)$` — prefix stripped | `^/(.+)$` — leading slash present |
| File test | `%{REQUEST_FILENAME}` | `%{DOCUMENT_ROOT}%{REQUEST_URI}` |

`REQUEST_FILENAME` is not populated this early. Use it here and the condition
silently never matches, so CSS and JavaScript get sent to ColdFusion.

**Do not also ship a `.htaccess` that rewrites.** It reintroduces the internal
redirect for anything it matches. There is deliberately no `.htaccess` in
`public/` for this reason.

## Requirements

- Document root is `public/`, not the project root. Otherwise `app/`,
  `resources/`, `tests/` and `.cfconfig.json` are reachable over HTTP, and the
  last of those holds the database credentials.
- `mod_rewrite` enabled.
- `/*.cfm/*` mounted, not only `/*.cfm`. `/index.cfm/about-us` does not *end* in
  `.cfm`. ColdFusion's generated `uriworkermap.properties` already has it.

## Diagnosing

Two steps settle almost anything. In the vhost:

```apache
LogLevel alert rewrite:trace6
```

```bash
curl -s -o /dev/null "http://example.com/about-us"
tail -60 /path/to/apache-error.log
```

Read the trace before changing anything.

- `[INTERNAL REDIRECT]` in that output is the failure described above.
- Its absence means the rewrite is being applied in place, and the problem is
  elsewhere.

If `/index.cfm/about-us` works while `/about-us` does not, then the application,
the routing, the mounts and ColdFusion are all fine *by definition* — the fault
is in the Apache-to-Tomcat hand-off, and nothing in this codebase needs to
change.

One trap while diagnosing: `JkLogFile` in ColdFusion's generated config may
point somewhere Apache cannot write, such as `/etc/apache2/`. mod_jk logging
then produces nothing at all, which reads as "mod_jk never saw the request"
rather than "the log is going nowhere".

## After a ColdFusion connector rebuild

`/opt/ColdFusion2023/config/wsconfig/<n>/` is generated by ColdFusion's
`wsconfig` tool. Re-running it overwrites that directory. Keep site-specific
`JkMount` and all rewrite rules in your own vhost so they survive.
